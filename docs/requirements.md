# 需求与约束

## 已确认

| 编号 | 方面 | 要求 |
| --- | --- | --- |
| R01 | 语言 | Rust 2024 edition。目标 MSRV 1.88，完整依赖闭包待实现验证。 |
| R02 | 界面模型 | 保留模式；界面状态跨输入事件与绘制帧存在。 |
| R03 | 布局 | 使用 Taffy；采用 0.14.0，Flex/Block 默认、Grid 可选，以低层树接口接入。 |
| R04 | 性能 | 以有 GPU、512 MB～1 GB 的 Linux ARM64 设备为首个资源基准，三平台桌面另做兼容验收。满足目标交互延迟后，依次优先空闲 CPU/唤醒、常驻 RAM、发布体积、额外帧吞吐。参考设备和工程预算见 resources.md，数值尚未实测。 |
| R05 | 模块化 | 文本、布局适配、绘制、平台接入等模块可分别使用；允许绕过默认组件库和标记语言、接入其他系统。模块自由组合，仅通过必要契约连接，禁止过度工程。 |
| R06 | 后端 | 多后端；支持 GPU 加速，偏好 Vulkan，不喜欢 wgpu。首版不使用 wgpu；Linux/Windows 使用 ash，macOS 使用原生 Metal。 |
| R07 | 平台 | 至少 Linux、Windows、macOS；Linux 优先 Wayland，不考虑 X11。 |
| R08 | 主要编写方式 | 使用简洁、直观、语义清晰、适合 AI 编写的标记语言为主要入口；支持构建期编译，以及独立可选的运行时加载。受限表达式与事件块、显式重载规则见 markup.md，不引入通用脚本 VM。 |
| R09 | Rust API | 控件创建一次，以句柄显式修改，事件驱动；不提供要求应用每帧重述界面的入口。API 极简命令式，参考 ImGui 的简短调用与 Tkinter 的直接操作，具体签名与所有权规则见 rust-api.md。 |
| R10 | Hello world | 程序不超过 10 行，包含初始化。按常规格式化后完整手写非空源码计数，标记路径合计启动代码与标记文件，不通过压行掩盖复杂性。 |
| R11 | 使用场景 | 首阶段覆盖三平台普通窗口；Linux 额外按需支持 layer-shell 面板/背景与多显示器。托盘、通知、全局快捷键等后续分别扩展；以 Quickshell 类项目为目标场景之一。 |
| R12 | 组件扩展 | 第三方能以很少的代码创建组件库，例如 MD3 风格组件库；提供尽可能完整且友好的组件创作能力。 |
| R13 | 文本 | 原生支持 CJK 字符显示，避免因预先装载大量字符造成内存膨胀；采用 Fontique/Parley/HarfRust/Swash，按需生成并分别限制缓存。 |
| R14 | 输入 | 原生支持 IME 文本输入与输入法交互；接入 Wayland text-input-v3、Windows TSF 与 macOS NSTextInputClient。 |
| R15 | 发布依赖 | 构建依赖体量不重要；发布依赖必须尽可能少且小。允许复用系统字体、驱动和平台库，逐项声明系统前提；精简系统按需打包。分别统计可执行文件、额外动态库和资产，静态链接代码仍计入体积。 |
| R16 | 验证 | 不编写大量测试；将来优先验证关键行为与资源目标，当前阶段只编写设计文档。 |
| R17 | 无障碍 | 必须提供完整系统无障碍语义及可检查的控件树，包括角色、名称、值、动作、焦点和关系；不要求每个控件均由平台原生控件实现。经用户决定，默认 desktop 不启用系统无障碍适配：Linux AT-SPI（引入 zbus 与异步运行时）与 Windows UIA 均为显式 feature；`accessibility` 单独提供可检查的语义树。支持范围与平台限制见 accessibility.md。 |
| R18 | 默认组件 | 默认组件采用跨平台一致、美观的中性极简外观，并适配深浅色、对比度和减少动态效果等系统偏好。视觉参数与首批组件清单见 components-theme-animation.md。 |
| R19 | 主题 | 框架原生提供主题系统及友好 API；无需依赖某个第三方组件库才能使用主题。采用有类型 token 和稀疏局部覆盖，规则见主题专题。 |
| R20 | 动画 | 框架原生提供动画系统及友好 API；统一时钟、默认补间、可选弹簧/关键帧，空闲无动画唤醒。 |
| R21 | 整体一致性 | 所有专题共同设计，组件、主题、动画、布局、绘制、文本、输入、无障碍与资源策略必须互相一致。 |
| R22 | 文档质量 | 按工业级工程设计文档的严谨程度编写，拆为多文件；包含需求追踪、契约、状态与生命周期、取舍、平台差异和验收条件，不用篇幅或机制数量替代质量。 |
| R23 | 绘制范围 | 基础绘制覆盖文字、矩形、圆角、边框、裁剪和位图；路径、SVG、渐变、阴影、模糊等纳入整体设计，作为按需选择的能力，逐后端说明支持、降级和成本。 |

## 需要消除的歧义

- “保留模式”约束界面的生命周期；“命令式”描述作者如何创建和修改界面，两者并不冲突。Q5 已选择创建一次、显式修改的方式。
- 标记语言支持构建期编译和可选运行时加载；这不等于已决定引入通用脚本虚拟机。
- “多后端”需要区分窗口系统接入与绘制实现：Wayland 和 Vulkan 分属不同职责，不能列为同一类互斥选项。
- “性能至上”不能直接推出最小 RAM、最小包体和最高帧吞吐同时成立；冲突顺序已由 Q2 确定，测量场景和目标预算见 resources.md，待实际验证。
- “极致拆分”不等于已经选定动态插件；独立使用范围已确认，具体依赖方向与发布组合见 modules.md。
- “依赖少”需要同时说明直接/传递依赖、静态链接代码、动态库、平台自带服务及随包资产，单看 Cargo 依赖数量不足以验收。
- “原生主题/动画”已确定为框架提供的能力；不能据此推断所有平台使用原生系统控件或系统绘制风格。
- “苹果那样的控件树”已由 Q10 明确为完整系统无障碍语义及可检查的控件树，不要求逐控件采用原生系统控件。
- “完整 API”需要以组件创作场景验证，不能简单等同于公开所有内部结构。
